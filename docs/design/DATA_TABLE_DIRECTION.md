# 数据表的定位：用户和 Agent 共同维护的结构化数据

状态：方向（2026-11-21，和用户讨论后定的；2026-11-24 补 3.4 文件格式 2、3.5 笔记列），部分实现，在 `feat/datatable` 分支上开发，短期内不合进 main。存储和引擎沿用 [DATA_TABLE_V2.md](DATA_TABLE_V2.md)；本文修正 [DATA_TABLE_PROGRESS.md](DATA_TABLE_PROGRESS.md) 里 2026-11-19「一个文件就是一张表、去掉关联」的简化。和代码对不上时以代码为准。

## 一、定位

> **Quiet.md 的数据表，是用户和 Agent 共同维护的结构化数据集。数据是主体；文档只是可以被关联的对象。**

典型场景：让一个 bot（比如 Grok）定期采集 X 评论区的反馈，整理成一张「X 反馈」表：链接、作者、时间、原文、摘要、情绪、类别、对应功能、处理状态。bot 每天往里写，人在 Quiet.md 里审阅、整理、关联到功能和设计文档。

它最重要的能力，是**比 CSV 装得下更复杂的结构**：

1. **字段有类型**：日期是日期，数字是数字，单选只能从选项里挑。CSV 里全是字符串。
2. **一格多值**：多选、多个附件、多个关联。CSV 只能自己约定 `a;b;c`。
3. **记录之间的关联**：一对多、多对多，两边都看得到。这是 CSV 完全做不到的，也是「维度」最多的地方。
4. **沿关联取值**：查找引用、汇总。比如功能表里统计每个功能收到几条负面反馈。

**多视图不是重点。** 看板、日历、画册这些「同一份数据换个角度看」的能力往后放；一个表格视图加上筛选、排序、分组，够人审阅就行。

## 二、为什么和 Notion、Obsidian Bases 不同

讨论时拿这两个当参照，结论如下：

| | Notion 数据库 | Obsidian Bases | Quiet.md 数据表 |
|---|---|---|---|
| 本质 | 带属性的文档集合，**装出来的**：数据库拥有页面 | 带属性的文档集合，**筛出来的**：对已有笔记的查询 | **结构化数据集** |
| 一行 | 一篇文档（属性 + 隐藏的正文） | 一篇笔记（frontmatter + 正文） | 一条数据，可以带笔记（3.5） |
| 属性定义在哪 | 数据库统一定义，类型来自固定列表 | 每篇笔记自己写，类型按属性名全库统一 | 表统一定义 |
| 规模 | 几十到几千行 | 跟笔记数一样 | 几千到几万行，持续增长 |
| 谁写 | 人 | 人 | 人和 Agent，Agent 往往写得更多 |
| 存在的价值 | 从整体上索引和管理所有文档的属性 | 同左 | 存放人和 Agent 采集的结构化数据 |

所以**不走「文件夹就是表、笔记就是记录」的路**（DATA_TABLE_V2.md 2.4 的 FolderSource 降为可选，不再是方向）。关联文档是顺带能力：某一格指向文档库里的一篇笔记，点开就是那篇笔记（V2 2.3 的「文档」字段）。

## 三、数据模型

文件格式沿用 V2 2.1：标准 SQLite，表名、列名就是界面上的名字，说明信息在 `_fields`、`_views`、`_meta`。概念对应如下：

| 概念 | 是什么 | 存在哪 |
|---|---|---|
| **数据集** | 一组相关的表，一起采集、一起维护。比如「X 反馈 + 功能」 | 一个 `.sqlite` 文件 |
| **表** | 一类数据 | 文件里的一张 SQL 表 |
| **字段** | 有名字和类型的一列 | SQL 列 + `_fields` 一行 |
| **记录** | 一条数据，有稳定的 `id` | 一行 |
| **关联** | 记录指向同一数据集里另一张表的记录 | 连接表 `表名.列名`（`from_id`, `to_id`），带外键 |
| **文档** | 记录指向文档库里的一篇笔记 | TEXT，相对路径 |
| **来源** | 这条记录是谁、什么时候写的 | 见下 |

### 3.1 一个文件是一个数据集，可以有多张表

2026-11-19 把界面简化成「一个文件一张表」，于是关联和查找引用失去了对象，这一轮（2026-11-21）还把旧文件里的这两种字段改成了只读。按新的定位，**关联要恢复成正式功能**，放在哪一层有两种选择：

- **A. 一个文件里装一组相关的表，关联只在文件内部（推荐）。** 文件格式本来就支持，外键和事务保证关联不会断；版本快照是整个文件，恢复时各表一致。代价是界面要重新有「切换表」，但不必恢复多视图。
- **B. 一个文件一张表，跨文件关联。** 每个文件更独立，但改名、移动、删除、恢复版本以后关联容易对不上，还要自己维护引用完整性。

推荐 A：「一个数据集一起采集、一起维护」本来就是一个单位。B 不做；需要连到别处时用「文档」字段指向笔记。

### 3.2 来源

Agent 会大量写入，必须能回答「这条是谁写的、哪次写的」，也要能撤掉一次写错的批量写入。每张表加四个系统列（下划线开头，界面里默认隐藏）：

- `_created_at`、`_updated_at`：ISO 8601 时间；
- `_created_by`、`_updated_by`：写入方，比如 `user`、`agent:grok-feedback`。

界面里改的一律记 `user`；通过第四节的接口写入的，记调用方报上来的名字。直接用 SQL 改、没填这几列的，读入时保持空，不猜。

### 3.3 唯一键

字段可以标成**唯一键**（记在 `_fields`）。按唯一键写入时，有就更新、没有就插入，bot 每天跑也不会重复。X 反馈表的唯一键就是推文链接。界面里填重复值时提示，不阻止（人工整理时允许暂时重复）。

### 3.4 文件格式 2（2026-11-24 定）

数据表还没正式对外，`.sqlite` 格式可以直接改，不为兼容妥协。目标是两份副本分开编辑后合并时不撞号，移动一行只写这一行。`_meta.format` 从 1 升到 2，分三个 PR 做完：

| 项 | 格式 2 | 哪个 PR |
|---|---|---|
| 记录 id | `INTEGER PRIMARY KEY`，随机整数，范围 [1, 2^53) | PR1（已做） |
| 表、字段、视图、选项 id | 随机整数，范围同上，整个文件内唯一；不再有 `next_id` | PR1（已做） |
| `_order` | TEXT 分数索引，按字符串比较；相同时按 id 排 | PR1（已做） |
| 行的元数据 | 拆成 `_created_at`、`_updated_at`、`_created_by`、`_updated_by`、`_auto` 列 | PR2（已做） |
| 关联 | 连接表 `表名.列名`（`from_id`、`to_id`），带外键 | PR3 |
| 唯一键 | 只在 `_fields` 里标记，不建 SQL 索引 | PR2（已做） |
| 单选、多选 | 仍然存选项名 | 不变 |
| 自动编号 | 仍然是连续号；同步合并时重新发号 | 不变 |

说明：

- **id 的上限是 2^53**：关联单元格把记录 id 写成 JSON 数字，JavaScript 读超过 2^53 的整数会丢精度。
- **id 从哪来**：`model.rs` 的 `IdGen`（splitmix64），平时用 v4 uuid 当种子，测试和 fuzz 固定种子，同一个种子结果相同。新 id 查重：表、字段、视图、选项在整个文件里不重复，记录在本表里不重复；撞了或是 0 就重抽。文件里不再写 `_meta.next_id` 和 `_tables.next_rec`。撤销、重做带着原来的 id，不重抽。
- **排序键**：`order.rs`，用 `board/fractional_index.rs`（rocicorp/fractional-indexing 的移植，CC0）生成 base62 键。内存里 `Table::records` 的顺序就是真正的顺序，键沿着它严格递增。移动、插入只给这一行新键；粘贴多行、新建表一次生成一串递增键。连续往同一个位置插 1000 次，键长 169；连续追加 1000 次，键长 3。
- **读入**：`_order` 是 TEXT 就直接用，按（键，id）排；相同的键、不合法的键、没有键（别的程序插的行，排在最后）由 `order::repair` 换新键，尽量少换。`_order` 是 INTEGER 或 REAL（格式 1，或别的程序写的）就按数字排好，再全部重新生成键。换了键的行在我们自己的表里标脏，打开时就写回去，格式 1 的文件就此就地升级成格式 2；别的程序建的表照旧，等第一次保存时整张重写。
- **来源列**：每张表开头依次是 `id`、`_order`、`_created_at`、`_updated_at`、`_created_by`、`_updated_by`、`_auto`，然后是字段。
  - 时间是 UTC 的 ISO 8601，带毫秒（`2027-01-15T00:02:03.123Z`），按字符串比较就是时间顺序。读的时候也认外部程序写的不带毫秒、不带时区（按 UTC）、带偏移（`+08:00`）的写法。内存里仍是本地挂钟毫秒，读写时按本机时区换算。
  - 写入方在 `Base::writer`（不存盘，默认 `user`）。新建记录记创建者和修改者，改单元格记修改者和修改时间，撤销、重做把这两项恢复原值。
  - 外部程序没填的 by 列读进来是空，不猜。时间没填按原规则：创建时间空用修改时间，都空用现在。`_auto` 空就发新号。自动编号、创建时间、修改时间字段的单元格仍可回补。
  - 读到还有 `_meta` 列的表（格式 1，或 PR2 之前的格式 2）：值从 JSON 里取，打开时整张表按新列重写。
  - 界面里暂不显示创建者、修改者，也没有对应的字段类型。
- **唯一键**：`FieldOpts::unique`，存在 `_fields.options` 里。
  - 能标的类型：文本、数字、URL、邮箱、电话、条码、单选（按选项名）。改成别的类型时去掉标记。
  - `Table::find_unique` 按唯一键找记录，`Table::duplicates` 列出值重复的记录组。比较规则：文本去掉首尾空白后精确比较（区分大小写），数字按数值（1 和 1.0 相同），空值不参与。
  - 只是标记，不阻止重复。界面开关和组合键以后再做。
- **坏 id**：读到 0、重复或 ≥ 2^53 的 id 就换掉。表、字段、视图、选项、记录都算；选项换了不要紧，单元格按选项名读。
  - 新 id 不从随机的 `IdGen` 取，而是确定的（`model::stable_id`）：对「种类、旧 id、所在表的 id（表本身用 0）、在文件里的序号」做 splitmix64 哈希，取到 [1, 2^53)。撞了已用的 id 就往后找，到上限回到 1。
  - 这样两台设备打开同一份坏文件，换出来的 id 一样，同步合并时不会变成一边删、一边增。`_tables` 没描述的表（别的程序建的）也这样取表 id，它的记录 id 就跟着确定。读入时现做出来的东西也一样：没描述的列猜出的字段、补上的默认视图、单元格里没见过的选项名加出的选项。
  - 被换掉的 ≥ 2^53 的 id，指向它的引用跟着改：表、字段的 id 改写关联的目标表和对侧字段、查找引用的 via / target，以及视图里的字段引用；记录 id 改写关联单元格。打开时就写回文件。
  - 新建记录、字段等正常发号仍用随机的 `IdGen`。
- 外部程序插入、没带 id 的行仍由 SQLite 的 rowid 给号；没有 `_fields` 的普通 SQLite 文件照样能打开。

### 3.5 笔记列（2026-11-24 定）

11-24 重新讨论过数据表的本质：A「表是文件，记录是数据」，还是 B「记录就是笔记，表是笔记的视图」（Notion、Obsidian Bases）。用户定的是：**本质是 A，再加一个「笔记」字段类型补上 A 写不了长文的缺点**。只有需要长文的表才加这一列，流水表（记账、日志、bot 采集）不受影响。

**交互**

- 字段类型「笔记」（`_fields.type = "note"`，归「高级」组）。一格对应一篇笔记。
- 表格里，格子显示笔记的标题；正文为空时显示淡色的「空笔记」。
- 点格子（或记录的「查看」）从右侧弹出记录面板，面板里完整展示这篇笔记，可以直接编辑，和在编辑器里打开一样（块、斜杠菜单、图片都能用）。面板可以拉宽，可以一键在主编辑区整页打开。
- 空的笔记格：点一下就新建一篇，标题取记录的首列（主字段）；首列为空时用「未命名」。重名照文档库的规则加序号。
- 也可以「指向已有笔记」：从库里挑一篇（@ 文档的选择器）。这种笔记不归表所有。
- 一张表可以有多个笔记列（比如「摘要」「读书笔记」）。

**存储（甲：真笔记文件）**

- 笔记是文档库里普通的 `.xml` 文档，全库搜索、@ 链接、反向引用、版本历史、同步都和别的笔记一样。`.sqlite` 里只存位置，长文不进按行合并。
- **笔记建在表格旁边的「<表名> · 笔记」文件夹里**（用户 2026-11-25 定：表格和 Markdown 一样没有子文档）：表格不挪位置，从空笔记格新建第一篇笔记时，才在表格旁边建一个普通文件夹 `Sources · 笔记/`，之后的笔记都放这里。这个文件夹是普通文件夹，表格改名时它不跟着改名（已有笔记照旧用它），用户可以自己改名、移动；笔记格里存的是相对表格的路径，笔记、表格或它们所在的文件夹改名移动时都会跟着改写。早先版本搬进同名文件夹的表格（`Sources/Sources.sqlite`）不自动拆开，新笔记照旧建在那个文件夹里；`crates/core/src/subdocs.rs` 仍把 `X/X.sqlite` 认作文件夹自己的文件。
- 单元格存**相对表文件的路径**（TEXT），规则和文档里的 `<cite type="doc" href>` 一样；读入时解析成运行时 id，写出时再换回路径，所以整个文件夹复制走链接仍然对。在应用里改名、移动笔记时，单元格跟着改（复用文档链接的那套）。在 Finder 里改了名找不到时，格子显示「找不到笔记」，可以重新指定。
- 删除记录：表所有的笔记一起移进回收站（和删除文件夹时带走里面的页面一样），撤销时一起回来；指向的外部笔记不动。删除笔记列：同上，先确认。
- 改记录的首列不会给笔记改名（v1），反过来也不会。
- 嵌在文档里的表（`.assets/<uuid>.sqlite`）v1 不能加笔记列：类型菜单里这一项灰掉，提示「独立的数据表才能加笔记列」。
- Agent 写入（第四节）以后可以带 Markdown 正文写进笔记列。

## 四、Agent 写入

V2 定的「文件优先、Agent 能直接读写」不变：任何人都能用 `sqlite3` 或 Python 直接改文件，应用已经每 2 秒检查一次文件有没有被外部改动（`src/table/mod.rs` 的 refresh 轮询），没有未保存的改动时就重新读入。

直接写 SQL 的问题是没人校验：类型可能写错、唯一键可能重复、来源不会记录，公式列也可能被改坏。所以再提供一个**官方写入方式**，让 Agent 优先用它：

| 操作 | 说明 |
|---|---|
| `schema` | 列出数据集里的表、字段、类型、单选和多选的选项、唯一键、关联指向哪张表 |
| `query` | 按条件取记录，结果是 JSON |
| `upsert` | 按唯一键写入一批记录，有则更新、无则插入，返回各条的 `id` 和新增 / 更新 / 未变 |
| `append` | 追加一批记录 |
| `add-field` | 加字段（类型、选项） |
| `link` | 建立或解除两条记录的关联 |

规则：

- 每次调用是**一个事务**，并且在写入前存一版快照（复用 `snapshot_table`），写错了可以在版本历史里整体恢复。
- 写入值按字段类型校验；单选写入不存在的选项时，默认报错，加参数才允许自动新建选项。
- 调用方必须报上自己的名字，写进来源列。
- 形式先做 CLI 子命令（Agent 都会跑命令），以后可以包一层 MCP。具体命令名、JSON 格式，实现时另定。

## 五、人怎么审阅

- 一个表格视图，加上筛选、排序、按单选分组。比如「本周未处理的负面反馈」。
- 来源列可以显示出来，按来源筛选：只看 bot 今天写进来的。
- 版本历史（已做）：Agent 写坏了能恢复整个文件。
- Agent 写入时用户正开着表、手上有没保存的改动：现在的做法是不重新读入，等用户的改动写完再说，会出现两边各写各的。实现官方写入接口时要处理：写入方等表空闲，或界面合并外部改动。

## 六、和现状的差距

| 项 | 现状（2026-11-21） | 要做的 |
|---|---|---|
| 存储格式 | SQLite，可以多表，有连接表 | 加来源列和唯一键标记；读旧文件时没有这些照常打开 |
| 关联、查找引用 | 新建字段里没有；旧字段只读 | 恢复成可新建、可编辑；汇总一起做 |
| 一个文件多张表 | 引擎支持，界面只显示一张 | 界面加切换表、新建表；内嵌 block 仍然只显示指定的那张 |
| 多视图 | 已去掉，只有一个表格视图 | 不恢复 |
| 筛选、排序、分组 | 引擎有，界面要核对 | 确认表格视图里都能用 |
| Agent 写入 | 只能直接写 SQL；外部改动 2 秒内读入 | 做第四节的接口 |
| 文档字段 | V2 设计过 | 做「这一格指向一篇笔记，点开打开它」 |
| 网页版 | 没有 SQLite，不能用数据表 | 不在本方向里 |

格式只增不改，旧版本读到新文件会忽略多出来的列和 `_fields` 里的新字段，不需要加 `store::FORMAT`。

## 七、分阶段

1. **关联回来**：关联、查找引用恢复可编辑；界面能切换和新建表。验收：在一个文件里建「X 反馈」和「功能」两张表，互相关联，功能表里查找引用反馈的情绪。
2. **汇总**：沿关联计数、求和等。验收：功能表里显示每个功能的负面反馈数。
3. **来源和唯一键**：系统列、唯一键标记、界面里能显示和筛选来源。
4. **Agent 写入接口**：`schema` / `query` / `upsert` / `append` / `add-field` / `link`，写入前自动快照。验收：一个脚本按推文链接重复写同一批数据，表里不重复，来源正确，能从版本历史撤回。
5. **审阅**：筛选、排序、分组在表格视图里好用；外部写入和本地编辑同时发生时不丢数据。
6. **笔记列**（11-24 提前，见 3.5）：一格一篇笔记，右侧面板里完整展示和编辑。验收：给「读书清单」加一个笔记列，点格子新建笔记写一段带图片的读书笔记，全库搜索搜得到，删记录后笔记进回收站、撤销回来。

## 八、还没定的

- 写入接口的形式：CLI 子命令叫什么、Agent 怎么找到文档库和数据集（路径还是名字）。
- 来源列要不要对用户可见、能不能改名。
- 唯一键是否允许组合键（多个字段一起唯一）。
- 一个数据集里的表很多时，内嵌 block 和侧栏怎么呈现。
