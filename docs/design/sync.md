## 1. iCloud

### 1.1 库放在哪

- **第一期**：支持用户把库放在 iCloud 云盘里的任意位置，比如 `~/Library/Mobile Documents/com~apple~CloudDocs/Quiet.md`，或者打开了"桌面与文稿"同步的 `~/Documents/Quiet.md`。这条路不需要额外的签名权限，现在就有用户这么用，只是不安全。
- **为 iOS 铺路**：iOS 访问 iCloud 云盘里的文件夹有两种方式：
  - 一是用户在"文件"里选一个文件夹，app 保存一个带安全作用域的书签；
  - 二是放在 app 自己的 iCloud 容器里（`iCloud~com~s1dashu~quietmd/Documents`，在"文件"App 里显示成 Quiet.md 文件夹）。

  移动端草案（M5）推荐 iOS 默认用后者，未登录 iCloud 时退回本机沙盒，"打开其他文件夹"放到第二版。
- **桌面端怎么接容器（和移动端对齐后的新思路，待实测）**：Mac 版是 Developer ID 签名、**没有沙盒**的 app，不用加 iCloud 权限，直接按路径打开 `~/Library/Mobile Documents/iCloud~com~s1dashu~quietmd/Documents` 就是一个普通文件夹，和"库放在 iCloud 云盘任意位置"走同一套代码。原来"先验证 Developer ID 能不能用容器"因此不再阻塞。要实测的是：
  1. iOS 版建了容器以后，**Mac 上没装任何带这个容器权限的 app 时**，访达的 iCloud 云盘里是否照样出现 `Quiet.md` 文件夹、文件是否双向同步；
  2. 非沙盒进程按路径写进去的文件，iOS 上能否看到，`NSFileCoordinator` 和 `NSFileVersion` 在这个路径上是否照常工作；
  3. "优化 Mac 存储"打开时，容器里的文件是否同样会变成占位（按 1.2 处理）。

  实测通过：桌面端第一期允许任意文件夹，另在"设置 › 文档库"和新建库时给一个"移到 iCloud 云盘（和 iPhone/iPad 共用）"，目标就是这个容器路径。实测不通过：退回原方案，桌面端给 app 加 iCloud 权限，再验证 Developer ID 能不能用容器。见 D12。
- 不论哪种，文件格式在容器里和在普通文件夹里完全一样。

### 1.2 占位文件（文件还没下载到本机）

| 平台 | 表现 | 处理 |
|---|---|---|
| macOS 13 及更早；iOS 的部分场景 | 文件被换成 `.名字.xml.icloud` | 已在处理：列表里显示，打开时报"还在从 iCloud 下载"。要补上：调用 `startDownloadingUbiquitousItem` 主动触发下载，下载完自动打开 |
| macOS 14+（基于 File Provider） | 文件名不变，但数据不在本地（dataless）。读取会阻塞，直到下载完 | 所有读取都放到后台线程（`store.rs:307` 已经注意到这一点）。读之前先查 `NSURLUbiquitousItemDownloadingStatusKey`，没下载就显示"下载中"，不要卡在读取上 |
| Windows iCloud 客户端（Cloud Files API） | 文件名不变，带"仅在线"属性，读取时自动下载 | 同上，读取放后台。用 `FILE_ATTRIBUTE_RECALL_ON_DATA_ACCESS` 判断。**需要在 sida-windows 上实测** |

关键补充：**`.quiet/` 里的文件也会被"优化存储"清出本地。** 读设备元数据文件时如果遇到占位，先触发下载再合并，不能把读不到当成空。现在的 index 恢复逻辑会把"读不出来"当成损坏，这一点需要改。

### 1.3 冲突副本

- **Apple 平台**：如果写文件时经过 `NSFileCoordinator`，并注册了 `NSFilePresenter`，iCloud 不会生成 `X 2.xml`，而是把冲突版本挂在 `NSFileVersion.unresolvedConflictVersionsOfItem` 上，等 app 来处理。我们现在是直接写文件（POSIX 先写临时文件再 rename），所以会看到 `X 2.xml` 这类副本。
- **第一期做法**：
  1. **Apple 平台（macOS 和 iOS）上写入改为经过 `NSFileCoordinator`**：vfs 里加一层，两个平台共用同一份实现。iOS 上访问 iCloud 容器**必须**经过文件协调，所以这不是 macOS 的可选优化，而是 iOS 的前提。冲突来自 `NSFileVersion` 时，把冲突版本取出来，交给第 3.2 节的三方合并，处理完调 `resolved = true`，再删掉旧版本。
  2. **兜底识别副本文件**：识别 iCloud 的 `名字 2.xml`，以及 Windows 客户端可能用的其他命名（需实测）。规则：同一目录下存在 `名字.xml`，**并且**任何一台设备的元数据里都没有这个文件，**并且**它的创建时间晚于原文件的最后同步时间。满足这些就当成冲突副本：不在列表里显示成新文档，把它当作"对方的版本"送进合并，合并完删掉副本。
  3. **把我们自己的重名后缀从 ` 2` 改成 ` (2)`**，消除歧义（见决策点 D8）。已有的 ` 2` 文件在元数据里有记录，不会被误认。

### 1.4 文件监听和延迟

- 加文件监听：macOS 用 FSEvents，Windows 用 ReadDirectoryChangesW，可以用 `notify` crate。Apple 平台再加 `NSFilePresenter`，它能收到"别的进程要写这个文件"的协调通知。现在每 2 秒一次的形状轮询（第 0 节）保留作兜底：监听收不到事件的文件系统（网络盘、部分第三方同步盘）还靠它，监听正常时把间隔放长到 30 秒。
- iOS：app 进入后台会被挂起，监听也停。回到前台时整体比对一次（和桌面"窗口重新激活"一样）；进入后台（`resign active`）时立即把防抖中的保存写出去，不等 500ms。
- **延迟的事实**：本机 iCloud 进程写到磁盘后，FSEvents 几乎立刻通知；但从一台设备传到另一台通常要几秒到几分钟，Windows 客户端更慢，而且不可控。所以"两边都改过同一篇"的窗口不小，合并必须是**日常路径**，不是罕见情况。
- 收到变化时，比较三个哈希：磁盘内容、基准快照（第 3.1 节）、编辑器里的内容：
  - 磁盘等于基准：是我们自己写的，或者没变化，忽略；
  - 磁盘变了，编辑器没有未保存的改动：静默重新加载，保留光标位置，撤销栈照现有"从磁盘重新加载"的逻辑处理；
  - 磁盘变了，编辑器也有未保存的改动：三方合并（基准、编辑器内容、磁盘内容）。
- 合并防抖 1 秒。文件写到一半时 iCloud 会先写临时文件，所以只认 rename 完成后的那次事件。

### 1.6 多台设备同时开着应用时怎么处理 `.lock`

- flock 跨设备没用。另一台机器看到的只是一个被同步过来的空文件，锁不住，还会被同步来同步去。
- 方案：
  - 锁挪到本机应用数据，只保护**同一台机器上的多个进程**（应用的多个实例、`quiet` CLI）。现在支持同时开多个实例，这点保持不变。有了多个顶层文件夹主页以后，每个顶层文件夹一把锁，文件名用文件夹 key（见第 3.6 节）。
  - 跨设备不加锁。正确性靠两点保证：元数据每台设备只写自己的文件，所以不会有两台设备写同一个文件；正文靠三方合并。
  - 迁移时删掉库里的 `.quiet/.lock`。
- 设备 id：首次运行时生成一个 UUID，存在本机应用数据里。同一台机器的多个实例、CLI、所有顶层文件夹共用它，由本机锁互斥。设备名用系统主机名，只用来在界面上显示"来自 iPad 的版本"。

### 1.7 其他要补的坑

- **Unicode 规范化**：同一个文件名，macOS 上可能是 NFD，Windows 上是 NFC。元数据里的路径一律存 NFC，比较时也统一转成 NFC。
- **大小写**：Windows 和 macOS 默认不区分大小写，`free_name` 已经按小写判重，元数据也要按小写去比较。
- **临时文件**：`.uuid.tmp` 是以点开头的文件，会被短暂同步出去。Apple 平台改用 `NSFileCoordinator` 写入后，这个问题就没了；Windows 上保持现状。
- **Git 仓库放在 iCloud 里**：`.git` 放在 iCloud 云盘里，是公认容易损坏的用法。第一期的 GitHub 同步本地不建 `.git`（2.1），没有这个问题；但同一个顶层文件夹仍然只能开一种同步（D13）。用户自己的 git 仓库放在 iCloud 里，我们不管，也不在那个顶层文件夹上开以后的 c 模式。

## 2. Git

### 2.1 实现：第一期直接调 GitHub API

用户 2026-11-22 定的原则：iCloud 和 GitHub 要长期支持、不挡以后的扩展；尽量少加依赖、控制包体积；配置越少越好，面向普通用户而不是只给开发者。按这几条重新比较：

| 方案 | 用户要做什么 | 包体积 | 远端 | 限制 |
|---|---|---|---|---|
| **a. GitHub REST API（Git Data API）** | 点「登录 GitHub」，选或新建一个仓库 | **几乎为 0**：HTTP 走应用已经在用的系统 `curl`（`update.rs`、字体下载都是这么做的），JSON、base64、解压（`miniz_oxide`）都已有，只多我们自己的一两千行代码 | 只 GitHub（GitHub Enterprise 换个 API 地址即可） | 登录用户每小时 5000 次请求；不支持 LFS；单文件 100MB 上限（和 GitHub 本身一样） |
| b. gix 只开最小特性，走 HTTPS | 同 a，也要先 OAuth 登录拿 token | **实测 +8.2 MB**：gix 0.90 最小特性（HTTPS 传输、`rustls`、检出、状态、提交），release + LTO + strip，arm64，空程序 0.35 MB → 8.54 MB；现在应用本体 39 MB。还会引入 rustls/ring，本机交叉编译 Windows 已知会卡在 ring | 任意 git 远端 | **gix 0.90 还不能 push**（源码里 push 只有 `push.default` 配置的解析），推送得另想办法，第一期不可行 |
| c. 调用系统 git | 自己装 git，配好 SSH 或凭据 | 0 | 任意 | Windows 默认没装 git，Mac 要先装命令行工具；iOS 用不了 |

**推荐**（D1）：
- **第一期做 a**，同步后端放在一个 `SyncRemote` trait 后面（列出远端改动、取文件、基于某个版本提交），以后加后端只换实现，不动合并和界面；
- **c 作为以后的「高级：使用本机 git 仓库」**，给已经有本地仓库、在终端里用 git 的开发者；
- **b 等 gix 支持 push 以后再评估**，到时用它覆盖 GitLab、自建 git 等非 GitHub 远端；
- iOS 上 a 的逻辑不变，HTTP 层换成 `NSURLSession`（iOS 不能起子进程调 curl）。

**a 的做法**：
- 本地文件夹**不是 git 工作区**（没有 `.git`）。远端是一个普通的 GitHub 仓库，用户在别处 `git clone` 下来就是同一个文件夹。
- 本机记录：`quiet-md/sync/<文件夹 key>/github.json` 记仓库、分支、上次同步到的 commit；基准快照（3.1）照用，存上次同步时每个文件的内容。
- **拉取**：先查远端分支的 head 变没变；变了就用 compare 接口（`上次 commit...head`）拿改动的文件列表，逐个取内容。新设备首次下载用 tarball 接口：gzip 用现有的 `miniz_oxide` 解，tar 格式很简单，自己读，约一百行。
- **推送**：给本地改过的文件建 blob → 以上次的 tree 为底建新 tree → 建 commit（父提交 = 远端 head）→ 更新分支，`force=false`。这期间远端被别的设备推过，接口会拒绝：先拉取、合并，再推。
- **合并全在本机**：基准 = 基准快照里上次同步时的内容，我方 = 磁盘，对方 = 远端最新内容，调同一个 `merge3`。所以 a 不需要 git 的合并驱动（2.6 只给 c 用）。
- 历史是线性的：每次同步一个 commit，父提交是远端最新，从不改写已推送的提交。

### 2.2 认证：第一期就做「登录 GitHub」

- **OAuth 设备码流程**：应用显示一个 8 位码，同时打开 github.com/login/device，用户在浏览器里确认就行。不用复制 token，不用配回调地址。
- **注册成 GitHub App，不用 OAuth App**：GitHub App 可以只授权用户选中的仓库（权限：Contents 读写、Metadata 只读），token 8 小时过期，靠 refresh token 自动续期；OAuth App 要 `repo` 权限，等于能动用户所有仓库。设备码流程不需要 client secret，client id 可以直接内置。**需要我们先在 GitHub 上注册这个 App（待办，用户操作）。**
- **新建仓库**：GitHub App 的用户 token 能不能直接替用户建私有仓库，要实测。不行就打开预填好的 `github.com/new?name=quiet-notes&visibility=private`，用户点一次「Create repository」，回来在列表里选中它。
- **token 存系统钥匙串**：macOS 用 Keychain（通过已有的 `core-foundation`/`objc` 调 Security framework，不调 `security` 命令行，免得 token 出现在进程参数里）；Windows 用凭据管理器（已有的 `windows` crate 加 `Win32_Security_Credentials` 特性）；Linux 第一期存在本机数据目录、权限 0600 的文件里。绝不写进库里。
- 调 curl 时，token 从 stdin 以配置的形式传入（`curl --config -`），不出现在命令行参数里。
- 高级选项：可以改填 PAT（GitHub Enterprise，或者不想装 App 的人）；以后的 c 模式用系统 git 自己的凭据。

### 2.3 什么时候同步

- **提交**：编辑停顿 60 秒；切换文档、关闭窗口、退出应用时；手动「立即同步」时。不在每次自动保存（500ms）时提交，否则提交多得没法看。提交说明自动生成，比如 `周报、提案 (MacBook)`；作者是登录的 GitHub 账号。
- a 模式下，一次「同步」= 拉取、合并、推送一个 commit，本地没有"积压的提交"。离线时改动就留在磁盘上，联网后一次推上去。
- **拉取**：启动时、窗口重新激活时、每 5 分钟一次、推送之前。
- **状态**：侧栏底部只显示四种：已同步 / 同步中 / 离线（有 N 处改动待上传）/ 出错。点「出错」看用人话写的原因和建议（"登录已过期，点这里重新登录"），不直接甩 git 或 HTTP 的报错。

### 2.5 图片和大文件

- `.assets/` 里的图片以 UUID 命名、写入后不再修改，正适合放进 Git，不会产生冲突。
- GitHub 单个文件有 100MB 的硬上限，超过 50MB 会警告。第一期规则：
  - 超过 50MB 的附件，提交前在界面里提示一下；
  - 超过 100MB 的不提交，并明确告诉用户哪篇文档的哪个附件同步不了。不要悄悄加进 `.gitignore`，那样另一台设备上的引用会坏掉。
- **Git LFS**：如果用户的仓库已经配置了 LFS（`.gitattributes` 里有 `filter=lfs`），系统 git 会自动处理。第一期不替用户开 LFS。
- 名字是原文件名的附件可能撞名（两台设备各插入一个 `截图.png`）。插入附件时一律改用 UUID 命名，原文件名存在 `name=` 属性里，现在附件已经有 `name`。

### 2.6 冲突怎么接上同一套三方合并

**第一期的 a 模式在应用内合并**（见 2.1），不需要下面这些。下面是给以后的 c 模式（本机 git 仓库）和"用户自己在终端里 `git pull`"准备的：用 Git 的**自定义合并驱动**：

- `.gitattributes`（入库）里写 `*.xml merge=quietmd` 和 `*.md merge=quietmd`；
- `.git/config`（本机，由应用写入）里写 `merge.quietmd.driver = "<quiet_md 路径> --merge-driver %O %A %B %P"`。

这样做的好处：

- Git 会把**共同祖先 %O、我方 %A、对方 %B** 三个文件交给我们，共同祖先直接用 merge-base，不需要第 3.1 节的基准快照。
- 用户在终端里 `git pull` 时也走同一套合并，结果和应用内完全一致。
- 合并驱动就是第 3.2 节的 `merge3`。全部自动合并成功时写回 %A 并返回 0；有冲突时，我方版本写回 %A，对方版本另存为冲突副本文件（第 3.2 节），同样返回 0，让 merge 能完成，再由应用在界面上提示冲突。
- 设备元数据文件按设备拆分后，正常情况下不会冲突：每台设备只改自己的文件。万一冲突（比如同一台设备的旧克隆），按字段时间戳合并，同样走合并驱动：`.quiet/meta/*.json merge=quietmd-meta`。
- 数据表文件：`*.sqlite merge=quietmd-table`，按行合并（第 3.5 节）。再加 `*.sqlite diff=quietmd-table`，配合本机的 `diff.quietmd-table.textconv`，让 `git log -p` 和 `git diff` 显示成文本（每行一条记录），历史就看得懂了。
- 其他二进制文件冲突时（极少见，因为 UUID 命名），两份都保留，对方的版本加后缀另存。
- 合并方式（c 模式）：**merge commit**，不用 rebase，不改写已经推上去的提交。a 模式是线性历史（2.1）。

如果系统里的 `quiet_md` 路径变了（比如更新后应用被移动），每次启动时重写 `.git/config` 里的驱动路径。

### 2.7 用户已经有自己的仓库时

**a 模式**（第一期）：登录后列出用户授权给 App 的仓库，选一个，或者新建一个。第一次同步没有基准，按两边有没有内容决定：
- 远端是空的：把本地上传上去；
- 本地是空的（新设备）：把远端下载下来；
- 两边都有内容：默认「下载到一个新文件夹」，作为一个新的顶层文件夹打开，最安全；另一个选项是「合并两边」，同名但内容不同的文件都生成冲突副本，不丢任何一边。

只上传 Quiet.md 管理的文件（D10），规则同下。

**c 模式**（以后的高级选项，本机已有 git 仓库）：
- 用户选的库目录**本身就是仓库根目录**：直接用，不 `git init`，用当前分支和它的 upstream。没有 upstream 就让用户选一个 remote 或分支。
- 库目录在**仓库的子目录**里（比如整个 dotfiles 仓库的一部分）：所有 git 操作都加 pathspec 限定在库目录里，提交时只包含库里的改动。
- **只 `git add` Quiet.md 管理的文件**：文档（`.xml`、`.md`、`.excalidraw`）、`.assets/`、需要同步的 `.quiet/` 文件。用户放在库里的其他东西（比如 `.obsidian/`）不碰，避免替用户提交不想提交的内容（决策点 D10）。
- 开启 Git 同步时，如果工作区已经有未提交的改动，先给出说明并请用户确认：要么由我们提交一次"开始用 Quiet.md 同步"，要么让用户自己先处理。
- 不改用户的 hooks、分支保护和签名设置；commit 签名照用户的 git 配置走。
- 从零开始：可以 `git init` 加填 remote URL，也可以从已有的远端克隆一个库下来（新设备加入时）。

## 3. 两边共用的部分

```text
            ┌────────── iCloud 路径 ──────────┐        ┌──────── Git 路径 ────────┐
            文件监听 / NSFileVersion / 冲突副本            git fetch + merge
                       │                                      │
              基准 = 本机基准快照（3.1）                基准 = merge-base（%O）
                       └──────────────┬───────────────────────┘
                                      ▼
                    merge3(base, ours, theirs)（fdl_core，3.2）
                       │                         │
                  全部自动合并               有冲突的块
                       │                         │
                  写回、重载编辑器        我方写回 + 对方另存冲突副本 + 横幅提示
```

### 3.1 基准快照（iCloud 没有共同祖先）

- 存在**本机应用数据** `quiet-md/sync/<文件夹 key>/`，不同步，每台设备各存一份：
  - `bases/<hash>`：按内容哈希存的正文，相同内容只存一份；
  - `state.json`：`{ "<NFC 相对路径>": { "hash": "<hash>", "size": 1234, "mtime": 1763800000 } }`，记的是本机最后一次**读到**或**写下**这个文件时的内容。
  - 哈希用 git 的 blob SHA-1（`sha1("blob <长度>\0" + 内容)`，即 `git hash-object` 的结果，`sync_base::blob_sha`）：和 GitHub tree 里的 blob sha 一致，GitHub 模式不用下载就能比较本地和远端的文件。
- 什么时候更新：本机保存成功后；从磁盘加载或重新加载文件后；合并完成写回后。这正是现在内存里 `Store::loaded`（保存时用来判断"磁盘被别人改过"的基准）更新的时机，基准快照可以理解为把 `loaded` 落盘、并扩到没打开的文件，两者在同一处维护。
- 清理：`state.json` 不再引用的哈希文件，每天清理一次。总量通常不超过库里正文的大小，正文都是文本，通常只有几十 MB。
- 基准丢了（换电脑、清缓存）：退化成两方比较。两边不一样，就当作冲突，另存一份冲突副本，不会丢数据，只是多一次让用户挑。
- 为什么不用历史快照当基准：历史快照存的是**保存前**的内容，有 5 分钟节流，还可能被保留上限清掉，不能保证就是"上次同步时的版本"。
- Git 模式不需要这个目录，merge-base 就是共同祖先。

### 3.2 按块三方合并

放在 `fdl_core::merge`（`crates/core/src/merge.rs`，已实现），不依赖 GPUI。iCloud、GitHub 后端、以后的合并驱动和 iOS 都调用同一个函数：

```rust
pub enum Merge { Clean(Document), Conflicts { merged: Document, regions: Vec<Conflict> } }
pub enum Conflict { Title, Icon, Cover, Blocks { parent: Vec<usize>, start: usize, len: usize } }
pub fn merge3(base: &Document, ours: &Document, theirs: &Document) -> Merge;
```

**算法**（第一期，没有稳定块 id）：

1. 三份内容由调用方解析成 `Document`。Markdown 文档按 Markdown 解析，合并完再按原格式写回。
2. **块的内容**：用 DocxXML 序列化（不含块 id）当作块的身份比较。
3. **对齐**（base↔ours、base↔theirs 各一次）：先去掉两头相同的部分，中间做精确 LCS；精确匹配之间的空隙里再配"改过的块"：
   - 空隙两边块数相同、类型逐个一致：逐个配对，当作原地修改（和 `changes.rs` 的做法一致）；
   - 否则按顺序，同类型、字符二元组 Dice 系数 ≥ 0.5 的配成同一块（两端补边界符，单字段落也能比）；
   - 空隙太大（超过 3000×3000 的一半面积）不做 LCS，只靠两头。
4. **diff3**：在 base 里两边都找到对应块的叫锚点。
   - 锚点之间的空隙：哪边和 base 一样就取另一边；两边一样就取任一边；base 这里是空的（两边都在同一处新增）就**两段都留、我方在前**，不算冲突；其余是冲突，取我方。
   - 锚点本身：一边没改取另一边；两边都改了，就把块拆成"自身"（文字、类型、属性）和子块：自身三方比较，两边改得不同就取我方、记冲突；子块递归做同样的合并（列表项、引用、高亮块、分栏都适用）。
   - 合并出来的自身不允许有子块（比如一边把段落改成代码块，另一边在它下面缩进了内容）：整块取我方，记冲突。
5. **块内文字**：第一期不做块内合并，两边改了同一段就算冲突（D14）。
6. 标题、图标、封面：分别按字段三方合并，两边改得不同就取我方，记冲突。
7. 结构保证：容器合并后变空（两边各删了一个子块）就补一个空段落；整篇变空就留一个空段落。

**测试**（`merge/tests.rs`）：固定用例覆盖常见情况；两组随机测试，种子数用 `FDL_FUZZ_SEEDS` 调（已跑过 5000）：
- 随机生成嵌套文档，两边各做随机编辑再合并：不 panic，结构合法，序列化后能原样读回；一边没改时结果等于另一边；两边改成一样时等于这一份。
- 两边只改相隔至少三段的段落（编辑、改写、删除、插入）：合并必须没有冲突，并且等于依次应用两边的改动。
- 5000 段的文档，两边各改 500 段，合并在 5 秒内完成（实测远低于此）。

**冲突时**（第一期）：

- **主文档写回"我方 + 所有能自动合并的部分"**，冲突区取我方的内容。
- **对方的完整版本另存为冲突副本**，放在同一个文件夹，名字形如 `周报（冲突 · iPad · 11-22 14:30）.xml`，并在元数据里标记 `conflict_of: <原文档 id>`，界面据此识别。
- 打开原文档时显示横幅："这篇文档和 iPad 上的修改有冲突（N 处）"，三个按钮：
  - **对比**：复用历史版本的只读预览和块级高亮（`changes::block_changes`），冲突块标红；
  - **采用对方版本**：走现有的"恢复版本"流程（先强制存一份快照，所以可以撤回）；
  - **保留两份**：取消横幅，冲突副本作为普通文档留下。
- 解决后自动删掉冲突副本，删除进回收站，可以找回。
- 第二期再做逐块挑选的界面：冲突区并排显示两个版本，每处选"我的 / 对方的 / 都要"。

这个方案始终不会丢数据，最坏情况是多出一篇冲突副本；而且大量复用了现有的历史预览、改动高亮和恢复功能。

GitHub 模式（`remote::engine`，合并用 `DocMerger` 调 `merge_file`）的基准取上次同步 commit 里这个文件的远端 blob（本机按 sha 缓存，缓存没了就按 sha 向远端取），不用 3.1 的本机快照。

### 3.3 元数据按设备拆分的文件格式

`.quiet/meta/<设备id>.json`，每台设备只写自己的这一个：

```json
{
  "v": 1,
  "device": { "id": "9b2f…", "name": "Sida 的 MacBook", "platform": "macos" },
  "items": {
    "3e5c9916-…": {
      "path":     ["Work/周报.xml",            1763800000123],
      "created":  [1763700000,                 1763700000000],
      "pinned":   [true,                       1763800000456],
      "starred":  [1763800000,                 1763800000456],
      "order":    ["a0V",                      1763800001000],
      "width":    ["wide",                     1763700000000]
    },
    "7d1a…": {
      "path":     ["Work/",                    1763700000000]
    },
    "c41e…": {
      "trashed":  [{ "from": "旧稿.xml", "at": 1763800002 }, 1763800002000]
    }
  }
}
```

- **每个字段是 `[值, 时间戳]`**。时间戳用混合逻辑时钟（HLC）：取 `max(本机毫秒时间, 本机见过的最大时间戳 + 1)`。设备时钟偏一些也能保证因果顺序。时间戳相同就比较设备 id，保证结果确定。
- **读取时的合并视图** = 所有设备文件里，每个 (条目 id, 字段) 取时间戳最大的值。合并结果缓存在本机（取代现在的 `index.json` 的位置），启动时如果设备文件没变就直接用缓存。
- **条目 id**：
  - 应用内新建的文档或文件夹：生成 UUID 并写入元数据，和现在一样；
  - 外部加进来的文件（Finder、git pull），还没有任何设备的元数据：**id = 首次发现时 NFC 相对路径的哈希**，和 `mounts::path_id` 同一种做法。这样两台设备各自发现同一个文件时，会算出相同的 id，不会各起一个。
  - 万一一个路径被两个 id 认领（比如重命名的同时对方又新建了同名文件），按"时间戳较早的 id 胜"处理，另一个 id 的字段合并过去。
- **路径**：`path` 也是一个后写者胜的字段。重命名或移动时，文件系统操作和元数据里 `path` 的更新一起发生。另一台设备先收到文件移动、后收到元数据（或者反过来）时，用"文件在磁盘上的实际位置"为准，`path` 只是帮助把 id 对回到文件上。
- **排序**：`order` 改成**分数索引字符串**（白板里已经有 `board/fractional_index`）。现在调整一项的顺序可能要给很多兄弟项重新编号，每次都会改动一大批字段；改成分数索引以后，只改被移动的那一项，并发调整顺序时也不容易打架。
- **删除**：`trashed` 也是一个字段，恢复就写 `trashed: [null, 新时间戳]`。永久删除写成墓碑 `purged`，30 天后清理。
- **压缩**：设备只重写自己的文件，并且只写**仍由自己"胜出"的字段**。被别的设备覆盖的值可以从自己的文件里删掉，文件就不会越写越大。
- **旧设备**：设备文件一直保留，不会损害正确性。设置里给出"移除已停用的设备"，把它的胜出字段并入当前设备后删除文件。
- **只属于本机的字段**（`opened`、窗口尺寸）不进这个文件，维持现在的本机存储。
- **FORMAT**：这是一次 `store::FORMAT` 4 → 5 的升级。旧版本看到 5 会拒绝打开，这个行为已经存在。迁移时把现有 `index.json` 的内容写成当前设备的元数据文件，时间戳全部用迁移那一刻的时间。库在同步盘上时，沿用 FORMAT 4 迁移时"先征得用户同意"的流程。

### 3.4 稳定块 id：第一期要不要做

**做法设想**：每个块在 DocxXML 里多一个属性，比如 `<p bid="k3f9a2">`，打开时读进 `BlockId`。复制粘贴时重新生成，拆分、合并块时按规则继承。Markdown 文件没地方放 id，只能继续按内容对齐。

| | 做 | 不做 |
|---|---|---|
| 合并精度 | 块的对应关系是确定的：移动、改写、相同内容的块（空段落、分割线）都能准确对上 | 靠 LCS 加相似度去猜，大多数情况下猜得对 |
| 文件 | 每个块多十来个字节，文件变大约 5–15%；Git diff 里多一些噪音 | 文件干净 |
| 兼容 | 旧版本会丢掉不认识的属性吗？要核对。如果会丢，只是 id 失效，不会读错内容，所以**不需要为它升 FORMAT**，随时可以加 | 无 |
| 工作量 | 解析、序列化、复制粘贴和块拆合规则都要改；`all-blocks.xml` 固定样例和往返测试要更新；导出到飞书时要去掉 | 无 |
| 将来 | 块级链接、评论锚点、实时协作的基础 | 到时再加 |

**不做时，精度到底差多少**（按单人多设备的常见情况）：

| 情况 | 有 id | 没有 id（LCS + 相似度） |
|---|---|---|
| 两边改了不同的段落（最常见） | 自动合并 | 自动合并，**没有差别** |
| 一边加段落，一边改别的段落 | 自动合并 | 自动合并，没有差别 |
| 两边改了同一段 | 冲突 | 冲突，没有差别 |
| 一边大幅改写某段（相似度 < 0.6），另一边改了相邻段落 | 自动合并 | 大概率仍能自动合并（相邻段落是稳定锚点） |
| 一边移动了某段，另一边改了这段 | 自动合并 | **变成冲突**（被认成"删了又加了一段"），生成冲突副本，不丢数据 |
| 文档里有很多一模一样的块（空段落、分割线） | 精确 | 偶尔对齐到另一个相同的块上，因为内容相同，最终结果通常一样 |

**推荐第一期不做**，理由：

- 常见情况没有差别；
- 差的那种情况会退化成"让用户挑"，不会丢数据；
- 加这个属性不需要升 FORMAT，以后随时可以补。

第一期把相似度配对做好；等有了逐块挑选的界面，或者要做块级链接和评论时，再一起做（决策点 D7）。

### 3.5 数据表（SQLite 文件）

数据表计划下个版本放出，所以第一期必须覆盖。现状是：数据存在 SQLite 文件里（`.assets/<uuid>.sqlite`，或者独立的表格文件）。已经用 `journal_mode=DELETE`，没有 `-wal` 和 `-shm`，这一点做对了。但还有三个问题：

1. **原地写入**：保存时在原文件上开事务。iCloud 正在上传时，文件被原地改写，可能传上去一个写到一半的文件；事务期间旁边还会短暂出现 `-journal`。
2. **二进制文件冲突没法按文本合并**：iCloud 只会生成 `表 2.sqlite`，Git 只会报冲突。
3. **整文件后写者胜会直接丢数据**：A 机加了 3 行，B 机改了 2 个单元格，只能保留一边。

**可选方案**：

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| A. 整文件后写者胜 + 冲突副本 | 两边都改了，就保留较新的那份，较旧的另存为 `表（冲突 · iPad）.sqlite` | 实现最简单 | 用户要自己对照两张表手工合并，数据表里这几乎做不到 |
| B. 同步格式换成文本 | 库里存 JSON 或 CSV（每条记录一行），SQLite 只当本机缓存 | Git diff 好看，能复用文本合并 | 改了数据表的存储格式（外部程序直接打开 `.sqlite` 的能力就没了），而且距离发布太近 |
| **C. 按行三方合并** | 三份文件都读成 `Base` 模型，按记录 `id` 合并（已有主键），细节见下 | 常见情况全自动，不丢数据；存储格式不变 | 要写一个表级合并函数，但有主键，比正文的块合并简单 |

**推荐 C**（决策点 D16）。合并规则：

- **共同祖先**：iCloud 用第 3.1 节的基准快照，同样按内容哈希存整个 `.sqlite` 文件；Git 用合并驱动给的 %O。
- **记录**：按 `id` 对齐。
  - 只有一边新增或删除：照做；
  - 两边都改了同一条记录：**按单元格合并**，两边改的不是同一个字段就都保留；同一个单元格两边改成不同的值，就取 `_meta` 修改时间较新的那个，并记入冲突列表；
  - 一边删了，另一边改了：保留这条记录（不丢数据），记入冲突列表。
- **手动排序 `_order`**：按记录取较新的值，合并后重新紧凑编号。
- **字段（表结构）**：按字段名对齐。新增和删除照做；同一字段两边改了类型或选项，取较新的那边并记入冲突。计算列（公式、查找、自动编号）合并完重新算，不参与合并。
- **视图和表的顺序**（`_views`、`_tables`）：按视图后写者胜。
- **冲突时**：主文件写回合并结果；冲突单元格的另一个值连同记录 id、字段、来源设备，写进本机的冲突列表。表格上方显示横幅"有 N 个单元格和 iPad 上的修改冲突"，点开逐个查看，可以一键采用对方的值。这一点不同于正文：数据表不另存冲突副本，因为整表副本几乎没法对照。合并前的我方文件留在基准快照里，可以撤回。
- **写入方式改为先写副本再替换**：保存时先把原文件复制成临时文件（或用 SQLite 的 backup API），在副本上开事务写入，再原子 rename 回去；Apple 平台上还要经过 `NSFileCoordinator`。这样同步盘只会看到完整的旧文件或完整的新文件，原文件旁也不会再出现 `-journal`。代价是每次保存重写整个文件；数据表通常只有几 MB，加上保存本来就有防抖，可以接受。超大表（比如超过 50MB）以后再考虑增量方案。
- **只读兜底**：如果合并函数遇到看不懂的结构（比如外部程序改了表、多了未知列），不要硬合并，退回方案 A：较新的保留，较旧的另存为冲突副本，并明确提示。
- **测试**：在数据表现有的 `table/fuzz_tests.rs` 里加合并用例。随机生成 base，两边各做随机 op 再合并，断言：不 panic；两边改的单元格不重叠时，结果等于依次应用两边的 op。

### 3.6 和顶层文件夹模型（多个顶层文件夹）的关系

顶层文件夹草案（workspaces.md）（`workspaces.md`）把"一个文档库"改成"侧栏上挂着的一组顶层文件夹，每个顶层文件夹一个 `Store`"。用户 2026-11-22 定了两条（W2、W4），同步这边因此简化：

- **每个顶层文件夹都有自己的 `.quiet/`**（W2）：用户打开的普通文件夹里也直接生成 `.quiet/`，不再有"库数据放本机的干净的文件夹"。所以原来的 D17（干净的文件夹开同步前先"升级"、本机那份用什么格式）**作废**，同步这边也不再区分"同步文件 / 同步元数据"两层：元数据本来就在文件夹里，跟着文件夹走。
- **同步按顶层文件夹开，开同步不需要额外的迁移步骤。** 每个顶层文件夹自己选同步方式（不同步 / iCloud / Git），自己的 `.quiet/meta/<设备id>.json`、自己的基准快照目录（`quiet-md/sync/<文件夹 key>/`）、自己的本机锁。设备 id 全局一份，所有顶层文件夹共用。D13（同一个库不能同时开 iCloud 和 Git）按顶层文件夹判断：一个顶层文件夹在 iCloud 里、另一个顶层文件夹是 git 仓库，互不影响。
- **新打开的文件夹直接按当前格式（FORMAT 5）建 `.quiet/`**，不经过迁移。带旧格式 `.quiet/` 的文件夹（以前的 Quiet.md 库）走 FORMAT 4 → 5 迁移，先征得同意（W11）；库在同步盘上时同样先问。
- **文件夹是 git 仓库、但没在 Quiet.md 里开 Git 同步时**：`.quiet/` 会作为未跟踪的文件出现在 `git status` 里。不自动修改 `.gitignore`；第一次打开这个仓库时给一句提示"Quiet.md 的数据存在 .quiet/ 里"，带一个「加入 .gitignore」按钮，用户点了才按 2.4 写入那一段（只忽略本机那部分，元数据照样可以提交）。开了 Git 同步就按 2.4 自动写。（和主页会话对齐，2026-11-22）
- **全局设置挪到本机 `quiet-md/settings/`**（W4：所有顶层文件夹地位平等，最初建的文件夹也能移除，设置不能再寄放在某个顶层文件夹里）：偏好、快捷键、主题、表情，以及主页视图、侧栏宽度、版本保留数这类应用级界面状态。按文档记的阅读位置留在各自顶层文件夹的 `.quiet/` 里。跨设备同步设置见 D5：第一期不同步；以后的做法**不能重新引入特殊顶层文件夹**（比如"设置所在的顶层文件夹不能移除"）。
- **文件夹 key**：本机 `folders.json` 里每个顶层文件夹的随机 UUID，添加顶层文件夹时生成，**改名、移动都不变**；每台设备各自生成，不写进文件夹里的文件。锁 `locks/<文件夹 key>.lock`、基准快照 `sync/<文件夹 key>/` 都用它。不用路径算出的 `library_key`，因为顶层文件夹可以在侧栏里改名（W5，改名就是改磁盘上的文件夹名），key 一变基准就丢，会触发没必要的合并。旧的解析缓存和恢复目录按 `library_key` 命名，升级时改一次名。
- **整个顶层文件夹被改名或移动**（W5，workspaces.md 2.11）：基准快照 `state.json` 存的是文件夹内相对路径，文件夹 key 又不变，所以只要找到新位置，基准照样能用，不会触发合并。要处理的只是"找到新位置"：本机改名时主页直接更新路径；别的设备上（顶层文件夹在 iCloud 里被改名）监听会看到根目录消失，macOS 先用 bookmark 解析新位置，解析到就重新挂监听、整体比对一次；解析不到就按主页的规则显示"找不到"。Git：`.git` 跟着文件夹走，不受影响；顶层文件夹是仓库子目录时会产生一次整目录 rename，提交时用 `git add -A <旧路径> <新路径>`，pathspec 跟着更新。这一条放进 1c（监听层），不是 1d 独有。接口由主页提供（`workspace.rs`）：`relocate(key, new_path)` 更新路径并发出"顶层文件夹路径变了"事件，应用内改名也发同一个事件；`resolve_bookmark(key)` 在 macOS/iOS 上解析当前位置，失效返回"不可用"。1c 只接这一个事件。
- **id**：顶层文件夹实现里跨文件夹的 id 不加任何前缀（应用内新建的是 UUID，跨文件夹不会撞）。会撞的只有两种：整个文件夹连同 `.quiet/` 被复制了一份，以及 3.3 里"外部文件的 id = 相对路径的哈希"在两个顶层文件夹里遇到同一个相对路径。为了让路径哈希 id 在各设备上算得一样、又不在顶层文件夹之间撞，**路径哈希改成"库 id + 相对路径"的哈希**：每个顶层文件夹第一次建 `.quiet/` 时生成一个库 id，写进 `.quiet/format.json` 的 `id` 字段，随文件夹同步（顶层文件夹第一步已做：`Store::library_id()`、`renew_library_id()`，旧库打开时补上）。剩下的整夹复制，由主页的 `Store::rekey` 处理：后打开的那个顶层文件夹换一个新的库 id，并给撞号的 UUID 条目换新 id。设备元数据里存的都是这种文件夹内 id。文件夹 key（本机 `folders.json` 的 UUID）另作他用，只给本机数据命名（锁、基准快照、解析缓存），从不写进文件夹里的文件。（和主页会话对齐，2026-11-22）
- **顶层文件夹列表只在本机**（`folders.json` 等），不同步：A 电脑打开的文件夹不会出现在 B 电脑上。
- **iOS 第一版只有一个顶层文件夹**（M5：放在 iCloud 容器里）。桌面上把同一个容器路径作为一个顶层文件夹打开，就是和 iPhone/iPad 共用的那一份；其他顶层文件夹只在各自那台电脑上显示，文案要写清楚。
- **CLI**：路径从主页算起（第一段是顶层文件夹名，见 CLI.md），元数据写进那个顶层文件夹的 `meta/<设备id>.json`。

## 4. 分期

**先做共同基础，再做 iCloud，然后做 Git。** 共同基础占了大部分工作量，而且两边都要用：

| 步骤 | 内容 | 共用 |
|---|---|---|
| 1a 基础 | FORMAT 5：元数据按设备拆分（3.3）、锁和缩略图等挪回本机（1.5、1.6）、设备 id；重名后缀改成 ` (2)`；附件一律用 UUID 命名；数据表改为先写副本再替换（3.5）。**依赖：`quiet` CLI 要一起改**，见下文 | iCloud 和 Git 都用 |
| 1b 合并 | `fdl_core::merge3`（3.2）和数据表的按行合并（3.5），都加 fuzz 测试；冲突副本、横幅、对比视图（复用历史预览）；数据表的冲突单元格列表 | iCloud 和 Git 都用 |
| 1c 监听 | 文件监听（轮询降为兜底）、外部改动后静默重载（在现有 `refresh_external` 上扩展）、编辑中被改时合并；基准快照（3.1）；iOS 进入后台时立即保存 | 主要给 iCloud 用，Git pull 之后的重载也用到；iOS 必须 |
| 1d iCloud | **Apple 平台（macOS 和 iOS 共用）**：写入走 `NSFileCoordinator`，处理 `NSFileVersion` 冲突，占位文件主动下载；识别冲突副本；新建库或"设置 › 文档库"里可以选"移到 iCloud 云盘（和 iPhone/iPad 共用）"（容器路径，取决于 D12 实测）；在 sida-windows 上实测 Windows iCloud 客户端 | iCloud；Apple 部分 iOS 必须 |
| 1e GitHub | `SyncRemote` trait 和 GitHub API 后端（2.1）、「登录 GitHub」（设备码、钥匙串）、选或新建仓库、自动拉取 / 合并 / 推送、首次同步的三种情况（2.7）、`.gitignore`、大文件提示、状态显示 | 仅 GitHub |

**1a 和 `quiet` CLI 的关系**（CLI 是独立 crate `crates/cli`，提交在分支 `worktree-feat-cli` 的 `f93d9a5a`，还没合进 main；方案见那边的 `docs/design/CLI.md`。下面几条已按该分支代码核对）：

- CLI 和应用在同一台机器上，算**同一台设备**：共用本机设备 id 和本机写锁（挪到本机应用数据以后，CLI 用同一个路径）。它写入的元数据进当前设备的 `meta/<设备id>.json`。
- CLI 用 `Store::open_for_tools` 打开库（和 `open_at` 的区别只是不处理崩溃恢复副本），文档、新建、改名、移动、回收站、数据表都调 `Store` 的方法，**没有直接读写 `index.json` 或历史目录的代码**；它给 agent 的 skill 里也写明"不要碰 `.quiet/`"。所以 FORMAT 5 换成按设备拆分以后它会自动跟上。
- 要改的只有插图：它把图片直接 `std::fs::copy` 进 `.assets/`（`library.rs:127`、`session.rs:645`），绕过了 `vfs`，在 Apple 平台上也就绕过了 `NSFileCoordinator`。1a 里给 `Store` 加一个"复制附件进库"的方法（UUID 命名，见 2.5），CLI 改调它。
- CLI 写之前已经逐个比对磁盘内容，被别人改过就整批放弃、提示重读（`session.rs:631`）。这和三方合并不冲突：CLI 是一次性的批处理，放弃重来比合并更安全，第一期维持。
- CLI 分支把应用的"编辑器干净时收下外部版本"从 Markdown 扩到了 XML 文档（`refresh_external`）。1c 在这个基础上做，所以 **CLI 最好先于 1c 合进 main**。
- **基准快照**：CLI 保存成功后，同样要更新本机基准快照（第 3.1 节）。这一步放在 `Store` 的保存路径里，CLI 和应用就自动一致；否则应用会把 CLI 的写入误当成"别的设备改的"，触发一次没必要的合并。
- CLI 现在用"块内容指纹"做 ref，和 D7（稳定块 id 以后做）一致，这一期不用改。
- CLI 方案里设想的"应用在线标记"要放在本机应用数据里，不要放 `.quiet/`（见 1.5 的表）。

**D8 牵涉的两件在做的事**：

- **#358**（issue「文件夹不支持重命名」）：`layout.rs:39` 的 `name_fits` 把"AAA 2"当成"AAA"加了编号，所以把"AAA 2"改回"AAA"时会被当成"名字没变"直接跳过。修复 PR 是 #361（2026-11-22 开，待合）：只改 `store.rs` 的 `follow_title`（加 `renamed` 参数，`rename`、`write_doc`、`write_doc_against`、`file_history.rs` 的调用处跟着改）和测试，**不动 `name_fits` 和 ` 2` 后缀**。D8 的后缀改动等那个 PR 合并后再做，改的时候 `follow_title` 新加的分支也要认 ` (2)`。新规则：新建的重名一律用 ` (2)`；`name_fits` 和 `unnumbered` 同时认 ` 2` 和 ` (2)` 两种写法；已有的 ` 2` 文件**不改名**（用户看得见的名字，不能悄悄改），它们在元数据里有记录，不会被当成冲突副本。
- **#357**（会话 `local_60320387-…`，PR #360 待合；规则见该 PR 里 `docs/FORMAT.md` 的「Child pages: a folder's own document」）：文件夹 `X/` 里名字**精确等于**文件夹名的 `X/X.xml` 或 `X/X.md` 就是文件夹的正文，其余是子文档。只看磁盘，index 不加字段，FORMAT 不变；`.excalidraw`、`.sqlite` 永远不算正文；`X.xml` 和 `X.md` 并存时 `X.xml` 是正文。改名时先改文件夹名，再把文件改成「文件夹名.扩展名」；删除和移动作用于整个文件夹。同步时要注意：
  - **文件夹里的冲突副本没有歧义**：`方案/方案 2.xml`、`方案/方案 (conflicted copy).xml` 名字和文件夹不同，按规则本来就是普通子文档，不会被认成正文；兜底识别（1.3 第 2 步）照常把它当成正文的冲突副本并进合并。
  - **文件夹这一层的副本要单独处理**：两台设备同时把同一篇文档变成"文件夹 + 正文"时，iCloud 可能生成 `方案 2/`，里面的正文仍叫 `方案.xml`，按规则它**不再是这个文件夹的正文**，界面上会变成"文件夹 `方案 2` 下有一篇子文档 `方案`"。识别规则：任何设备的元数据里都没有这个文件夹，里面有一个和**去掉副本后缀后**的名字同名的文档，其余都是已知的子文档。满足就把正文送进合并、子文档并回 `方案/`，再删掉副本文件夹。
  - **改名的中间状态**：改名是两次文件系统操作（先文件夹、后文件），另一台设备可能先只收到第一步，看到 `新名/旧名.xml`，这时按规则文件夹暂时没有正文、`旧名.xml` 是一篇子文档。因为 index 不加字段，要靠设备元数据里该文档的 `path` 字段判断：`path` 已经是 `新名/新名.xml` 而磁盘上还是 `新名/旧名.xml` 时，当作改名进行中，仍按正文显示，等第二步到达；超过一段时间（比如 10 分钟）还没到，就由本机补做第二步。
  - 重名后缀规则对文件夹同样适用：新建的重名文件夹是 `方案 (2)/方案 (2).xml`。#360 没有改 `name_fits`、`unnumbered`、`free_name`，只调用了 `free_name`。改后缀时逻辑不用动，但 `subdocs.rs`（`follow_note_title`、`wrap_in_folder`）和 store 测试 `a_page_with_children_keeps_one_name` 里断言的 `甲 2/甲 2.xml`、`丙 2.xml` 要跟着改成 ` (2)`。

为什么先做 iCloud：

- 现在已经有用户把库放进 iCloud 用，`index.json` 冲突是已经存在的风险，先做等于先修 bug；
- 1a–1c 做完以后，iCloud 只剩平台适配要做。

Git 依赖的 1a 和 1b 都是共用的，Git 部分在 1d 进行的同时就可以并行开工。

## 5. 决策

用户 2026-11-22 定：**全部按推荐**，但要对照五条原则——iCloud 和 GitHub 长期支持、不挡扩展；文件夹自包含（包括它的设置和废纸篓）；少依赖、控制包体积；配置越少越好，面向普通用户；各条线并行推进。按这五条改过的是 D1、D2、D5、D13、D15，其余照原推荐。

### 5.1 按"配置越少越好"复查

| 环节 | 用户要做的 | 我们兜住的 |
|---|---|---|
| 开 GitHub 同步 | 点「登录 GitHub」→ 浏览器里确认 → 选或新建一个仓库 | 不用装 git、不用 SSH key、不用填 token；`.gitignore` 自动写；token 自动续期 |
| 新设备加入 GitHub 同步 | 登录 → 选同一个仓库 | 本地空就直接下载；两边都有内容时默认下载到新文件夹，不会把两份混在一起 |
| 开 iCloud 同步 | 点「移到 iCloud 云盘」（或者本来就把库放在 iCloud 云盘里） | 占位文件自动下载；冲突能合并的自动合并 |
| Windows 上用 iCloud | 装 Apple 的「iCloud for Windows」 | 这是唯一绕不开的前提，设置里给下载链接 |
| 冲突 | 只在两边改了同一段时看到横幅，三个按钮：对比 / 用对方的 / 两份都留 | 文案不出现"merge""冲突区"这类术语，写"和 iPad 上的修改撞了"；不会丢任何一边 |
| 出错 | 看状态里的一句话和一个按钮 | 不直接显示 git、HTTP 的原始报错；"登录过期"→「重新登录」，"文件超过 100MB"→ 指出是哪篇文档的哪个附件 |
| 同一个顶层文件夹同时开两种同步 | 不会走到这一步 | 一键二选一 |
| 数据表冲突 | 表格上方横幅，逐个查看，一键采用对方的值 | 不另存整表副本 |
| 设置 | 不用管 | 文件夹级设置跟着文件夹走；应用级设置换电脑时用一次导出 / 导入 |

需要用户（我们）做的准备：在 GitHub 上注册 Quiet.md 的 GitHub App（2.2）；D12 的三项实测；Windows iCloud 客户端实测（1.2、1.3）。前两项的逐步说明见 [sync-setup.md](sync-setup.md)。
