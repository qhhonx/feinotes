# 画板渲染压测结果

场景：`board_gen.py perf <n>`（n 个带文字的圆角矩形、相邻之间绑定的箭头、n/4 条 60 点笔迹；元素数约 3.25n）。脚本 `board_bench.txt`，跑法 `python3 tools/perf/board_bench.py`，`FDL_BOARD_RENDER=gpui|vello|auto` 选后端，`FDL_BOARD_PROF=1` 打印每次绘制的后端、可见元素数和耗时。

数字是 devtools `bench` 的 frame p50（ms，同步画一帧的 CPU 时间，不含 GPU 光栅化），M5 Pro、2x 屏、1280×800 窗口，2026-11-14。

- 全景平移：打开时适应全部内容（最小 10%，大场景只显示一部分，1000 起可见约 3000–7000 个元素），横竖来回滚动，四组平均；
- 悬停：指针在画上移动（命中测试 + 重绘），两组平均；
- 100% 平移：⌘0 后来回滚动（可见几十个元素），两组平均；
- 缩放：⌘= 一组、⌘- 两组平均。

改动前的主要开销：

1. 独立 `.excalidraw` 文件打开后，下面那篇文档里的画板缩略图每帧把整个场景再画一遍（看不见，10000 时约 250ms）。现在被打开的画板盖住时不画；缩略图可见元素 ≥ 64 时走 vello，画面不变就直接复用上一帧（滚动文档也不重画）。
2. 每帧对全部元素重建绘制顺序、查缓存（10000 时约 3.3ms）。现在场景不变（平移、缩放、悬停）时复用上次的顺序和外框，只做外框裁剪（0.2ms）。

阈值：可见元素 ≥ 800 切到 vello，< 500 切回 GPUI（迟滞，免得来回切）。约 650 个可见元素时两者 CPU 时间相当（n=200 全景）；再往上 GPUI 每个元素约 3–5µs 线性增长，vello 约 1.5µs，且 GPUI 还有这里没算的 GPU 光栅化（4× MSAA）。vello 每帧有约 1.5ms 的固定成本（整屏光栅化 + 拷进 IOSurface），可见元素少时不如 GPUI。悬停等不改场景的帧，vello 直接复用上一帧。

按键处理：⌘= / ⌘- 的 step（处理按键，不含绘制）原来随元素数线性增长（10000 时约 11.7ms，3000 时约 3.5ms）：`run.rs` 对每个 action 先复制整个元素数组，视口变化也走 store 提交（快照比对整个场景）。现在缩放类 action 只改视口、不复制也不提交，10000 时 0.02ms。

## 和原版 Excalidraw 对比（2026-11-15）

原版：npm `@excalidraw/excalidraw` 0.18.0 的生产构建，React 19，跑在应用内置浏览器（Chromium）里，1280×800、2x，页面是 `board_upstream.html`。我们：本分支（rough.js 手绘渲染、自带字体），自动后端。两边用同一份 `board_gen.py perf` 场景，`roughness` 全改成 1（默认的手绘风格），缩放和步骤都对齐 `board_bench.txt`：全景按我们打开时的缩放（n=1000 为 12%，其余 10%）。

口径不完全相同：我们是 devtools `bench` 处理事件加同步画一帧的 CPU 时间（step + frame）；原版是每次派发事件后 150ms 内主线程的忙碌时间（含 React、画布绘制、GC），两边都不含 GPU 光栅化。都取 p50（ms），各组平均。

| n（元素数） | 场景 | 原版 | 我们 | 倍数 |
|---|---|---|---|---|
| 1000（3225） | 全景平移 | 12.7 | 4.6 | 2.8× |
| | 悬停 | 4.2 | 1.0 | 4× |
| | 100% 平移 | 2.8 | 1.4 | 2.0× |
| | 缩放 | 5.9 | 2.9 | 2.0× |
| 3000（9706） | 全景平移 | 26.4 | 10.2 | 2.6× |
| | 悬停 | 9.4 | 1.5 | 6× |
| | 100% 平移 | 8.9 | 1.5 | 6× |
| | 缩放 | 19.1 | 3.2 | 6× |
| 10000（32420） | 全景平移 | 47.1 | 13.2 | 3.6× |
| | 悬停 | 29.9 | 2.2 | 14× |
| | 100% 平移 | 20.4 | 1.6 | 13× |
| | 缩放 | 50.9 | 3.4 | 15× |

原版每帧都遍历全部元素（可见性判断、React 重渲染），所以只看得见几十个元素的 100% 平移也随场景变大而变慢；我们在场景不变时复用绘制顺序、只做外框裁剪，这类帧基本不随元素数增长。原版的 p95 常到 50–130ms（GC 和元素画布缓存重建），我们的 p95 在 20ms 以内。roughness 0 时我们的数字和 1 基本相同（rough 路径按元素缓存）。

悬停一行是 2026-11-15 修正后的数字：之前 `bench` 里的 `move` 发的是系统鼠标事件，bench 的同步更新期间窗口被借用，事件被丢掉，测到的只是一帧空绘制（本文件开头表格里的「悬停」一列同样不可信）。现在 bench 期间的指针移动直接交给 `Window::dispatch_event`（`src/devtools.rs`）。

## 拖拽延迟（2026-11-15）

`board_drag.txt`：100% 下按住一个两侧都绑了箭头的矩形，每步 4pt 来回拖（四组各 30 步），再 ⌘A 全选拖。原版用 `board_upstream.html` 的 `runDrag()`，同样的矩形、同样的步子。数字是一步的 p50（ms，我们是 step + frame），括号里是 p95。

| n（元素数） | 原版 | 优化前 | 现在 |
|---|---|---|---|
| 1000（3225） | 5.1（18–27） | 3.2 | 1.9（2.5） |
| 3000（9706） | 8.0（33–39） | 5.9 | 2.0（2.5） |
| 10000（32420） | 17.2（60–130） | 17.8 | 2.1（2.6） |

（更正：「优化前」和「现在」两列其实只是 frame，没加 step；拖一个元素时 step 约 0.08ms，影响不大。第二轮的数字见下一节，按 step + frame 算。）

全选拖（几乎每个元素都在动）：原版 65 / 395ms / 32420 个元素时页面卡住几秒；我们第一轮后是 23 / 64 / 243ms（step + frame）。

优化前一步的开销随元素总数线性增长，三处：

1. 属性面板每帧对全部元素做十几次「找选中元素」和建全量映射表（10000 时约占一半）。现在面板只拿选中元素、它们的标签和标签容器、正在编辑的文字来算（`BoardView::selection_scope`，选中超过 256 个时仍用全场景），`BoardView::selected_elements` 按 id 查表再按场景顺序排，不再扫描。
2. 拖动每一步把整个场景复制一份给吸附缓存，其实缓存建好之后就用不上。现在只在吸附要建缓存时才复制（`SnapCache::wants`）。
3. 场景一变（拖动时每帧都变）绘制顺序就整表重建：筛可见元素、逐个查缓存。现在元素数组没增删、没换顺序、没改绑定时，只更新版本变了的元素（和它的标签 / 容器）的缓存和外框（`render.rs` 的 `Order`）；分区变了（子元素的裁剪跟着变）或改动超过八分之一时仍整表重建。

### 第二轮（2026-11-15）

`bench` 现在分两次更新：先处理事件，让它的 effect 和 observer 跑完（和真实事件一样），再画一帧；step 包含前者。下面都是 step + frame 的 p50（ms），括号里是 p95。

| n（元素数） | 拖一个元素 | 全选拖 | 悬停（10000，指针真的在移动） |
|---|---|---|---|
| 1000（3225） | 1.7（2.6） | 5.7（7–9） | |
| 3000（9706） | 2.0（2.4–5.8） | 10.4（12–15） | |
| 10000（32420） | 1.9（2.6–8） | 25.4（28） | 0.9（1.3），第一轮后 2.4 |

全选拖第一轮后是 23 / 64 / 243ms。在一篇长文档（`all-blocks` 的内容重复 6 遍）里打开画板拖一个元素：1.5 → 0.9ms。

改了什么：

1. 只是平移的元素不再重新生成图形。`Scene::translate_element` 改 x/y、记下「从哪个版本只平移到了哪个版本」（`Scene::translation`）；绘制缓存发现元素（和它的标签、容器、框架）都只是同样平移过，就把外框和裁剪平移过去，图形本身等真要画时才挪 origin（`render.rs` 的 `moved_by` / `settle`）。上游也是这样：`ShapeCache` 只在尺寸、点变了时作废。
2. `drag_selected_elements` 不再把每个元素复制四遍，原始外框每次拖动只算一次，一步里只读一次时钟（`with_one_timestamp`）；没开吸附时不准备吸附数据。
3. 属性面板的结果缓存到选区、app 状态或选中元素（平移除外）变了为止（`properties::cached_model`、`BoardView::scope_stamp`）。
4. 选中框只给画布里看得见的元素建、画。
5. 命中测试用 256×256 的网格索引（`canvas::HitIndex`），场景变后第二次命中测试才建，拖动中每步一次的命中测试不重建。
6. 画板界面（工具栏、面板、底栏）是单独的缓存视图（`chrome::ChromeView`）：悬停和拖动选区时，app 状态和选中元素（平移除外）没变就复用上一帧的布局和绘制，其余变化照常重画。A/B：拖一个元素每帧 2.76 → 2.45ms。
7. 画板盖住整个窗口时，下面的文档和侧栏的行不再渲染（侧栏保留宽度占位，文档布局不变）：拖一个元素每帧约省 0.5ms（侧栏）和 0.65ms（长文档）。
8. GPUI Metal 渲染器把路径顶点直接写进 instance buffer（vendor 补丁 36），提交一帧从约 0.84ms 降到约 0.21ms。这部分在 `bench` 的计时之外（帧提交发生在之后的系统回调里），是用 `sample` 量的。

## 三个平台同一套后端（2026-11-16）

vello 后端原来只在 macOS（IOSurface 像素缓冲 + Metal surface 管线）；现在三个平台相同：帧拷进 `PixelFrame`，用 GPUI 的 `Window::paint_pixels` 当图片精灵显示（图集块原地重写，vendor/PATCHES.md #36），文字轮廓来自 CoreText / DirectWrite / swash（#37）。macOS 上逐像素截图和改动前完全一致；vello 帧平移多约 0.5–0.9ms（多一次拷进图集）。

Windows（i5-13600KF、RTX 4070 Ti、1280×800 窗口），`board_bench.txt` 同口径（step + frame p50，ms）：

| 场景 | 可见元素 | 改动前（只有 GPUI） | 现在（自动） |
|---|---|---|---|
| n=1000 全景平移 | 约 3100 | 13.5–16.3 | 8.5–13.3 |
| n=3000 全景平移 | 约 5300 | 20.7–41.2 | 12.1–22.1 |
| n=10000 全景平移 | 约 5300 | 40.3–46.3 | 14.2–19.6 |
| n=3000 / 10000 悬停 | 约 5300 | 37.9–39.2 | 1.5–2.3 |
| 100% 平移、缩放、带图画板 | 50–400 | 2–7 | 2–7（仍是 GPUI） |

vello 在 Windows 上每帧的固定成本约 5–6ms（macOS 约 3.5ms），可见元素少时不如 GPUI，所以阈值不变。Linux（WSL2 / WSLg，X11，lavapipe 软件 Vulkan，窗口较小、全景约 1190 个可见元素）：n=3000 / 10000 全景平移 GPUI 4.7–5.8ms，vello 1.1–2.0ms。
