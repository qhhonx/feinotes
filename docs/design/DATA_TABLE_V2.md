# 数据表 v2：设计方案

状态：方案（2026-11-17），未实现。取代 DATA_TABLE.md 记录的第一版（照飞书描 UI、内存 JSON 模型）。第一版在飞书上实测的尺寸和交互细节仍然有用，引擎和存储重做。

## 一、已定的方向

1. **文件优先（file over app），而且 Agent 能直接读写。** 一个数据库是文档库里的一个标准 SQLite 文件。不依赖 Quiet.md，用 `sqlite3` 命令、Python 或任何 SQLite 工具都能读写；文件里的表名、列名、取值就是用户在界面上看到的。
2. **引擎按成熟开源项目的源码移植，不靠看界面猜。** 做法和画板移植 Excalidraw 一样：钉住一个上游提交，逐模块对照移植，上游的单元测试一起搬过来。
3. **交互完成度对标飞书多维表格和 Airtable；界面是 Quiet.md 自己的**，用现有 `Theme` token，不照搬任何一家的外观。
4. **不引入数据库服务。** 不用 PostgreSQL。SQLite 只当文件格式用，计算在内存里做。

## 二、存储：一个 SQLite 文件

一个数据库在文档库里是一个文件：`读书清单.sqlite`。它是标准的 SQLite 3 数据库，里面可以有一张或多张互相关联的表。扩展名直接用 `.sqlite`，人和 Agent 一看就知道该用什么打开。

选 SQLite 而不是 CSV 或 xlsx 的理由（2026-11-17 定）：

- **Agent 读写最方便。** macOS 和 Linux 自带 `sqlite3` 命令，Python 自带 `sqlite3` 模块。Agent 可以先看表结构，再用 SQL 只取需要的行，不必把整个文件读进上下文。
- 列有类型，每行有稳定的 id，一个文件里能放多张表，关联用真正的外键。
- 改一格只写一格，不重写整个文件；写入是事务，中途崩溃不会坏文件。
- 格式公开、向后兼容，是长期保存的推荐格式。

### 2.1 文件里的结构：让不认识 Quiet.md 的人和 Agent 也能看懂

原则：**打开文件执行 `.tables` 和 `select * from 读书清单`，看到的就是用户在界面上看到的那张表。** 不用内部编号当表名和列名，不把一行塞进一个 JSON。

- **每张数据表是一张 SQL 表**，表名就是用户起的表名，列名就是用户起的列名。另有两列：`id INTEGER PRIMARY KEY`、`_order`（手动排序用的分数索引）。
- **每格的存法：**

| 字段类型 | SQL 里的存法 |
|---|---|
| 文本、长文本、超链接 | TEXT |
| 数字、货币、百分比、进度、评分 | INTEGER / REAL（显示格式记在 `_fields`） |
| 日期 | TEXT，ISO 8601：`2026-11-17` 或 `2026-11-17T09:30` |
| 复选框 | INTEGER，1 / 0 |
| 单选 | TEXT，选项名 |
| 多选 | TEXT，JSON 数组：`["小说","科幻"]`（SQLite 的 JSON 函数可以直接查） |
| 附件 | TEXT，JSON 数组，元素是相对路径；文件放 `.assets` |
| 关联 | 一张连接表 `表名.列名`（`from_id`, `to_id`），带外键 |
| 文档（行的正文） | TEXT，相对路径，指向一篇普通笔记 |
| 公式、查找引用、汇总 | **算出来的结果**也存成普通的列，Agent 和别的工具不用懂公式就能读到值 |

- **说明信息也是普通的表**，下划线开头：
  - `_fields`：每列一行：所属的表、列名、类型、选项（名字 + 颜色槽位）、显示格式、公式表达式、列宽、位置。
  - `_views`：每个视图一行：所属的表、名字、类型、筛选 / 排序 / 分组 / 隐藏列 / 冻结 / 行高 / 统计（一个 JSON）。
  - `_meta`：格式版本、写入它的应用版本，以及一段给人和 Agent 看的说明文字（各表的含义、哪些列是算出来的不要直接改）。

### 2.2 读写方式

- 打开时把表读进内存，引擎在内存里算（筛选、排序、分组、公式）。每个 `Op` 在一个事务里写回对应的行或列，不重写整个文件。
- 日志模式用 `DELETE`，不用 WAL：磁盘上始终只有一个文件，不产生长期存在的 `-wal` / `-shm`，对同步盘更安全。
- **别的程序（包括 Agent）会直接改它。** 用文件监听加 `PRAGMA data_version` 发现外部改动，整表重新载入；读入时校验每格是否符合列的类型，不符合的照原样显示并标出来，不丢数据。公式列被外部改了，下次重算时覆盖。
- 没有 `_fields` 的 SQLite 文件也能打开：按 SQL 的列类型和内容推断字段类型。
- 用 `rusqlite`（MIT）自带的 SQLite，三个平台行为一致；体积增加约 1 MB（估计，未实测）。

### 2.3 行的正文（「行即页面」）

不给每行都建文件。表里可以有一列「文档」类型：

- 这一格空着，这行就是一条普通记录。
- 在行上点「展开」开始写正文时，才新建一篇普通笔记（放在和数据库同名的文件夹里），路径写进这一格。
- 展开一行看到的是：上面是这一行的各列（可编辑），下面是这篇笔记的正文。

正文留在普通的笔记文件里，不存进 SQLite：笔记仍然是文档库里独立可用、能被搜索到的文件。

### 2.4 另一种数据来源：一个文件夹的笔记（后做）

把一个文件夹里的笔记当成行、笔记开头的属性（frontmatter）当成列，和 Obsidian Bases 同一个思路。引擎用同一套，只是数据来源不同（见 3.1 的 `Source`）。放在第 6 阶段。

### 2.5 文档里的表格 block

block 只记「哪个文件、哪张表、哪个视图」：`<datatable src="读书清单.sqlite" table="读书清单" view="进行中"/>`，不把数据内嵌进文档。同一张表可以出现在多篇文档里，各自选不同的视图，改的是同一份数据。

### 2.6 导入和导出

CSV 和 xlsx 作为交换格式：拖进来转成 `.sqlite`，任何一张表、任何一个视图都能导出成 CSV 或 xlsx。

### 2.7 这样存的代价

- **普通用户双击打不开。** Excel、Numbers 不认 SQLite，文本编辑器里是乱码。靠 2.6 的导出补。
- **同步盘。** 应用正在写的瞬间被 iCloud / Dropbox 同步走，对方可能拿到不完整的文件；两台机器同时改会产生冲突副本，只能整文件二选一。用 `DELETE` 日志和短事务降低风险，不能完全消除。
- **不是文本**，git 看不了改动；版本历史要按整个文件存快照。
- 第一版的 `.table`（JSON）没有发过版，不迁移。旧版本不认识 `.sqlite`，会跳过，不需要加 `store::FORMAT`。

## 三、架构

和画板同样的分法：模型、算法、交互状态机放 `crates/core/src/table/`（不依赖 GPUI，能单测、能 fuzz），绘制和外壳放根 crate 的 `src/table/`。

```
src/table/                      GPUI：画网格、单元格编辑器、弹层、各视图外壳
crates/core/src/table/
  model/     字段类型、单元格值、校验、类型转换
  ops.rs     所有修改都是一个 Op，带逆操作
  query/     筛选、排序、分组、统计（内存里执行）
  formula/   词法、语法、类型检查、求值、函数表、依赖图
  source/    Source trait：SqliteSource、FolderSource
  codec/     导入和导出 CSV、xlsx
  grid/      无界面的网格：坐标、可见区域、选区、命中测试、交互状态机
```

### 3.1 各层的职责

- **model**：一个字段类型是一组行为：从文字解析、写回文字、校验、和别的类型互转、比较、默认显示格式。新增类型只加一个文件。
- **ops**：增删改列、增删改行、改格子、移动行列、改视图配置，全部是 `Op`，执行后返回逆 `Op`。撤销重做是 Op 栈（不再整表快照）；fuzz 随机生成 Op 序列，检查「执行再撤销回到原样」「存盘再读回不变」。每个 Op 对应一个 SQLite 事务。
- **query**：输入是表 + 视图配置，输出是「行的显示顺序 + 分组结构 + 统计值」。改一格只重算受影响的部分。
- **formula**：公式按行求值、按列名引用（`{单价} * {数量}`）。依赖图管公式、查找引用、汇总之间的重算顺序和循环引用报错。
- **source**：`Source` trait 把「行和列从哪来、改了写回哪」抽出来。先做 `SqliteSource`。
- **grid**：不碰 GPUI。输入是鼠标键盘事件和滚动位置，输出是「要画哪些格子、选区在哪、现在在拖什么」。这层让选区、填充柄、拖动换序这些交互能写单元测试。

和文档的集成沿用现有约定：表的改动经 `editor::Core`（`checkpoint` → Core 方法 → `Editor::changed()`），`fuzz_tests.rs` 的 `step` 加对应的随机操作。

### 3.2 移植的源头

全部是 MIT，移植的文件开头注明对应的上游文件，THIRD_PARTY.md 登记。

**主源：Teable** `github.com/teableio/teable` @ `b8425f5a60d056205adc456b9e8011ff7d622a29`（2026-11-17 的 develop）。根目录 LICENSE 写明 `packages/` 下全部 MIT（`apps/` 是 AGPL，不看不搬）；`core`、`sdk`、`formula` 三个包的 package.json 也都标 MIT。

| 我们的模块 | 上游目录 | 上游规模（不含测试） | 上游测试 |
|---|---|---|---|
| `model/` | `packages/core/src/models/field`（20 个字段类型） | 189 KB / 75 个文件 | 27 个文件 |
| `query/` 的定义部分 | `packages/core/src/models/view` | 56 KB / 31 | 5 |
| `formula/` 语法 | `packages/formula/src`（ANTLR 语法，改写成手写解析器） | — | — |
| `formula/` 求值和函数 | `packages/core/src/formula`（`visitor.ts`、`functions/`） | 约 110 KB | 6 |
| `grid/` | `packages/sdk/src/components/grid`（canvas 自绘：坐标、选区、区域命中、各渲染层） | 386 KB / 77 | 14 |
| 筛选面板、单元格编辑器的行为 | `packages/sdk/src/components/filter`、`editor`、`grid-enhancements` | 168 + 279 + 156 KB | 12 + 18 + 8 |

**辅源：**

- **AFFiNE data-view**（MIT）：`query/` 的执行部分。Teable 的筛选、排序、分组是在服务端用 SQL 执行的，包里只有定义；内存里怎么执行、怎么分层，参照 AFFiNE 的 `core/`（filter、sort、group-by、statistics）。
- **Glide Data Grid**（MIT）：`grid/` 的细节对照：大数据量的虚拟滚动、选区模型、填充柄。

**从上游删掉的**：多人协作、权限、评论、人员字段、创建人 / 修改人、按钮字段、计费、所有网络请求。

**上游没有、要自己写的**：SQLite 文件的读写和结构变更、类型推断、`Source`、内存里的查询执行、外部改动后的重新载入。

### 3.3 性能目标

- 10 万行 × 30 列：滚动不掉帧（只画可见格子，沿用画板的显示列表缓存思路）。
- 10 万行上改筛选或排序：100 毫秒内出结果。
- 打开 10 万行的表：1 秒内可交互。

压测脚本和结果放 `tools/perf/`，和画板一样留数字。

## 四、界面和交互

**交互的完成度靠清单，不靠印象。** 每个阶段开工前，先在飞书和 Airtable 上把这一阶段涉及的操作逐项实测，记成一张行为清单（做什么操作 → 发生什么），实现后逐项对照，harness 脚本回放截图。清单放本目录。

**外观的原则：**

- 颜色、阴影、弹层外壳只用 `Theme` 语义 token 和 `ui::popover` / `ui::menu_row`；深色模式跟随应用。第一版用的 `feishu_theme` 实测色不再用于界面。
- 表格是笔记的一部分，不是另一个应用：没有自己的顶栏和左侧导航，沿用应用的顶栏和面包屑；工具栏一行，默认只显示视图切换、筛选、排序、分组、搜索，其余收进「…」。
- 网格线尽量淡，表头不铺灰底；信息层次靠字重和留白，不靠线框。
- 选项标签、评分、进度、复选框这些格子里的小部件，尺寸和对齐按 4px 栅格统一。
- 所有会改变布局的操作（展开分组、拖动换序、改列宽、切视图）有过渡动画，时长统一。
- 键盘优先：方向键、Tab、Enter、直接打字进入编辑、⌘C/⌘V（和 Excel 互相粘贴）、⌘Z，全部和电子表格的习惯一致。

## 五、分阶段

每个阶段的验收：对应的上游测试移植后全部通过；fuzz 通过；行为清单逐项对上；`scripts/check.sh` 零警告。

| 阶段 | 内容 | 做完能用来干什么 |
|---|---|---|
| **0 地基** | 钉住上游提交、登记 THIRD_PARTY、列出文件对照表；SQLite 文件的读写（2.1 的结构）、类型推断；`Source`、`Op` 和撤销；往返测试和 fuzz；量出加入 SQLite 后的实际体积 | 应用写出的文件能用 `sqlite3` 直接查；外部建的 SQLite 文件能打开 |
| **1 网格** | 移植 `model/`（文本、长文本、数字及其显示格式、单选、多选、日期、复选框、评分、超链接）和 `grid/`；GPUI 绘制；区域选择、复制粘贴、填充柄、行列拖动换序、改列宽、冻结列、增删行列、改字段类型；10 万行性能 | 当一张好用的表格用 |
| **2 视图引擎** | 筛选（可嵌套的条件组）、多列排序、多级分组（可折叠）、底部统计行、隐藏列、行高、表内搜索；一张表多个表格视图 | 同一份数据按不同条件看 |
| **3 行和文档** | 展开一行（属性 + 正文）、「文档」列、附件列；文档里的表格 block 改成引用文件的视图，并能就地编辑 | 行即页面；表嵌进笔记 |
| **4 公式和关联** | 公式（解析、类型检查、求值、函数表、编辑器补全）；关联、查找引用、汇总；依赖图 | 跨表计算 |
| **5 更多视图** | 看板、画册、日历；之后再看甘特和表单 | |
| **6 数据来源和导入** | 文件夹笔记作为数据来源；导入导出 CSV / xlsx，导入飞书多维表格导出的文件 | |

阶段 0 和 1 是一起才有东西可看的，其余每个阶段单独能发版。

## 六、待定

1. 扩展名用 `.sqlite`（本文的写法）还是 `.db` 或自己的名字。
2. 一个文件里放多张表时，侧栏怎么显示：一项，点开后在里面切换表；还是展开成多项。
3. 版本历史怎么存：整文件快照，还是只记 Op。
4. 要不要顺带提供给 Agent 用的入口（命令行或 MCP），在直接改文件之外多一条带校验的路。
5. Markdown 笔记里能不能放表格 block。
